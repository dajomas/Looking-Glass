# Dedicated wall editor and UVTT export

## Workflow

From a map's fog editor, choose Walls → Open wall editor. Opening the screen
neither shows the map to players nor changes fog. It edits that map's current
walls, not an original uploaded source. Maps without walls can start from scratch.

Select Add wall and a type, then click its two endpoints. The nearest existing
endpoint within 10 screen pixels is used when snapping is enabled. Escape cancels
a pending start. Choose Remove wall, Change wall type or Edit, then click within
10 screen pixels of the target. Where lines overlap, the closest line wins;
equally close lines prefer the most recently listed segment. Zoom in to disambiguate.
Drag pans, wheel zooms, F fits. Undo/Redo covers up to 1000 draft operations;
Ctrl/Cmd+Z undoes, Ctrl/Cmd+Shift+Z redoes. Tools wait for metadata and artwork.

Save wall set commits the draft immediately with no Apply confirmation. In one
SQLite transaction it saves a wall-only UVTT source, replaces this map's segments,
bakes alignment into image pixels and resets calibration to identity. The original
source is never overwritten; identical generated bytes reuse a campaign source.
Changed versions have the same map-N-walls.uvtt filename but distinct source IDs.
The scene name is retained in the extension. Other maps remain unchanged.

Download UVTT exports the current draft, including unsaved edits, without saving
or applying. A downloaded draft can be uploaded through Saved wall sources later.
The image checkbox affects downloads only; stored reusable sources remain wall-only.
The canonical map image can be embedded as base64 for self-contained interchange.
An export without image is intended for wall reuse with a separately supplied map;
not every third-party VTT accepts wall-only files.

Pixels per grid defaults to 70. Choosing another value changes serialization
units, not the overlay's position or size. Export coordinates are calibrated
image pixels divided by pixels per grid; map_size uses the same units and
map_origin is zero. Reimport with auto-align restores the original size.

## Editing exact endpoints and wall type

1. In the wall editor, choose **Edit** in the Tool menu and left-click/tap a wall,
   or use **right-click / Ctrl+left-click** from any selected tool.
2. Click within 10 screen pixels of a wall. The nearest segment is selected;
   zoom in when several lines overlap. Right-drag still pans and does not select.
   The shortcut does not change the selected tool or perform its primary action.
   Opening the dialog cancels a pending Add-wall start. A miss leaves the draft
   and pending start unchanged. The browser context menu stays suppressed inside
   the map viewport; touch users can keep using Edit with a primary tap.
3. The modal opens with Endpoint 1 X/Y, Endpoint 2 X/Y and the wall type.
   Coordinates are calibrated map-image pixels, not screen pixels or grid units.
   In-bounds decimals retain full precision. Existing outside endpoints are shown
   at the nearest image edge with a correction notice; the draft remains unchanged
   until Apply. Finite values typed outside the image are clamped on Apply to
   X = 0..image width and Y = 0..image height. Missing/non-finite values are rejected.
   The endpoints must still differ after clamping.
4. Select any of the nine wall types and choose **Apply to draft**, or press Enter
   in a coordinate field. Validation errors keep the dialog and draft unchanged.
5. Use **Save wall set** to persist the draft and create/reuse its UVTT source,
   or **Download UVTT** to export the unsaved draft without applying it.

Applying changes is a single undoable operation covering both endpoints and type.
The map overlay updates immediately, retaining the screen-space width/zoom fix.
Cancel or Escape discards the dialog's fields without altering the draft, undo
history, saved walls or player display. Applying unchanged values is also a no-op.
The modal traps keyboard focus; Tab/Shift+Tab cycle through its fields/buttons,
input undo stays local to the input, and closing returns focus to the viewport.

Coordinate-only edits preserve an imported segment's blocking flag. Changing its
type uses the existing retyping rules: ethereal is non-blocking; other types are
blocking. Map-level disabled types and Doors split areas still apply when saving.
Endpoint snapping is not applied to typed coordinates. In-bounds values stay
exact; image-edge clamping applies independently to out-of-bounds values.

The popup does not send an HTTP request or autosave. Existing save/export APIs,
CSRF checks, stale-save protection and boundary safety guidance remain unchanged.
For installation and rollback, see [the Edit-tool patch note](../Patch/wall-editor-edit-tool.md)
and [the right-click shortcut update](../Patch/wall-editor-right-click-edit.md).

## Image-edge placement

With Add wall selected, a click/tap outside the artwork but inside the viewport
places the pending dot on the nearest image edge (or corner) instead of ignoring
the click. The second endpoint follows the same rule. Endpoint snapping also
uses bounded candidate coordinates, so an imported endpoint beyond the artwork
cannot pull a new point outside it.

Bounds are the image's coordinate rectangle: X from 0 through image width, Y
from 0 through image height, inclusively. They are not the browser viewport edges.
The same map coordinates are used after panning, zooming or fitting the map.
A second click that would create a zero-length segment is rejected as before.

A visible imported wall outside the artwork can be selected with Edit/right-click/
Ctrl+left-click. Its endpoint fields show the edge-clamped positions. Apply makes
that correction one undoable draft operation; Cancel/Escape preserves the original
outside coordinates. Merely loading/selecting a wall does not rewrite stored data.
Other unedited imported walls are retained, even if they extend beyond the image.
Saving and exporting continue to use the existing APIs and data format.

## Boundaries and safety

All nine kinds are editable, even if hidden or disabled in the fog editor.
New/retyped ethereal segments have blocks=false; other new/retyped kinds have
blocks=true. A coordinate-only Edit preserves the segment's imported blocking
flag. Existing imported blocking flags are retained for untouched segments. Show/Enabled
and Doors split areas remain map-level settings and are not baked into a wall set.
Thus a saved set can be reused on a map with different boundary settings.

Save retains fog operations and snapshots and notifies viewers through the
existing refresh path. It does not activate or blank the map. Blank players before
boundary edits during play: replayed reveals can expand when rooms merge. After
saving, inspect the exact player preview and reset fog if appropriate.

Nothing is autosaved. The page warns before leaving a modified draft. Reload
asks before discarding edits. Saving resets local undo/redo history. Version and
map-incarnation checks reject stale saves with 409, covering alignment, artwork,
wall edits and deletion/recreation. Download without image can rescue an old draft;
then reload saved walls and reconcile. Including artwork requires the original
artwork version/dimensions to match, otherwise 409 avoids attaching the wrong image.

The editor performs no background poll that could replace a draft. A separate
tab's saved-source menu may need Refresh sources. Server-side geometry, count and
export-size limits return explicit errors. Very large drafts can be slow to render;
there is no spatial index or grid-drawing tool in this patch. Request bodies are
parsed by FastAPI before generated-export size checks; existing deployment request
limits should still be used. External URLs and filesystem paths are never fetched
from UVTT data. Existing authorized canonical image storage is used for embedding.

## UVTT interchange and exact wall types

Core output uses UVTT format 0.2, resolution, line_of_sight,
objects_line_of_sight, portals, lights and environment fields. This is a wall
editor, not a scene-preservation editor: imported lights, arbitrary source metadata,
portal open states and source background settings are not retained or synthesized.
Normal doors are exported closed. No third-party VTT compatibility is claimed as tested.

| Looking Glass kind | Standard fallback | Exact reimport here |
|---|---|---|
| wall | line_of_sight | wall |
| door | closed portal | door |
| secret | line_of_sight, so it is not exposed as an obvious door | secret |
| window | line_of_sight | window |
| invisible | objects_line_of_sight; third-party treatment varies | invisible |
| ethereal or nonblocking segment | omitted from standard blockers | retained by extension |

The looking_glass extension has version=1, name, segments in grid units and a
SHA-256 checksum of the core geometry/resolution fields. Each segment stores
x1,y1,x2,y2,kind,blocks, preserving all kinds and passive segments. This is an
application extension, not a claim that core UVTT standardizes all ordinary types.
An unaware importer uses only fallback fields and may lose these distinctions.

The checksum detects another program changing standard geometry while leaving
stale extension coordinates. This case is rejected rather than silently importing
outdated walls. Remove the entire looking_glass field to import standard geometry
only, accepting type loss. An ordinary UVTT file with no extension follows the
existing parser unchanged. Unsupported extension versions are rejected explicitly.
Empty edited sets are valid and can be saved/reimported.

## Modules and compatibility

- services/uvtt_export.py: validation, standard geometry, lossless extension, JSON.
- services/foundry_import.py: recognizes the extension before ordinary UVTT parsing.
- web/admin/wall_editor.py: admin-only HTML, full-precision state, transactional save,
  draft download and saved-set download, using existing permission/CSRF dependencies.
- static/js/admin_wall_editor.js: draft editing using the existing PanZoom component.
- web_html/admin/wall_editor.html and static/css/wall_editor.css: separate UI.
- web/app_factory.py: mounts the router on the admin app only.

## Wall width matches the fog editor

The width slider uses the same screen-pixel base width in both editors. A normal
wall at 2 px has the same thickness in the wall editor and fog editor; each
0.5 px slider step changes the base width by 0.5 screen pixels in either editor.
The width is independent of map-image resolution and is compensated on every
zoom/redraw using `base_width / zoom_scale`.

Doors and secret doors in the wall editor now use the fog editor's double-width
category styling. At a 2 px base width these categories are 4 px wide. The fog
editor still uses its existing passive styling for non-blocking/disabled walls.
Dashed categories also use the same base-width-relative dash sizing.

The default remains 2 px. Existing per-map browser preferences are retained, so
if the width was previously increased to compensate for the mismatch, set it
back to the desired value. Width changes do not affect saved wall coordinates,
UVTT data, fog boundaries, or player images.


## Locked and unlocked doors

Both the Add/Change type selector and the endpoint-edit dialog include Locked Door and Unlocked Door. Locked Door uses dashed orange; Unlocked Door uses solid orange. Both use ordinary door-width strokes and can participate in area boundaries. Their Show and Enabled controls appear in the fog legend.

The wall editor always loads authored door types, not temporary lock changes made in the fog editor. Saving sets the new design and replaces wall rows, clearing runtime overrides for those replaced rows. During play double-click a locked arrow to unlock without revealing; double-click an unlocked arrow to lock. Reset restores authored types. To keep topology stable, type-enable settings follow the authored kind during runtime lock changes. Change and save the design to change that baseline.

Looking Glass UVTT extension data round-trips both types exactly. In standard UVTT geometry both are exported as closed portals, so tools ignoring the extension see ordinary closed doors and may lose the lock distinction. A Foundry ordinary door with `ds: 2` imports as Locked Door; other ordinary doors keep their existing Door classification. Secret doors remain secret.

## Passage configuration and portal pairs

Select Add wall with type Portal element and draw the sections. Converting a wall
through Change wall type or Edit also creates a new portal section. New sections
start with both sides Unconfigured; no Entry or Exit is invented on creation.
Only Portal elements appear in the portal-section and destination dropdowns.

Open Portal configuration and select one portal section. Only its two side panels
are shown. When a side is configured, the opposite side defaults to None only if
it was still Unconfigured. An explicitly configured opposite side is preserved.
Entry and Both roles show paired Exit portal-section and Exit-side selectors,
as well as initial lock/discovery state and secret post-discovery state.

Select an Exit, Unconfigured or None side on another Portal element. Selecting
Unconfigured/None changes it to Exit immediately within the popup, and its still
Unconfigured opposite side defaults to None. Apply commits the conversion and
route atomically to the draft; Cancel discards it. Both is still selectable and
retains its Entry role and configured states. Entry-only destination sides remain
disabled: configure them as Both first if they need to receive and send passages.
Shared exits remain supported. Both provides independently routed Entry and Exit
roles. All routes in a pair still use the same other section; unpair first to
change partners. No wall, door, self-route or third section can become a target.

Switching the selected section retains pending popup edits. Apply configuration
to draft commits changed popup edits in one Undo/Redo step, including any target-side
initialization, and keeps the popup open. Each successful Apply becomes the new
popup baseline. Repeating Apply without changes creates no additional undo step.
Close, Cancel pending edits and Escape discard only edits since the last Apply;
they never undo changes already applied to the editor draft. No popup action sends
an HTTP request. You may Apply an unfinished section while configuring another one;
Save wall set and Download reject unconfigured, unpaired or invalid portal graphs
before making a request. Finish all sections and routes before saving/exporting.
The existing server also validates complete graphs; its schema/API are unchanged.

Reset section / unpair resets the selected section and its partner together to
Unconfigured portal sections, preserving geometry and Portal type. This is pending
inside the popup until Apply; Cancel discards it. After Apply it is one undoable
draft operation. Sections can then be re-paired or removed/retyped individually.

Secret door Edit dialogs still include authored post-discovery type. Coordinate
edits preserve configuration; reversing endpoints swaps physical side locations
while retaining stored side indices. Portal panels, Exit selectors, errors and
map labels use compass headings with map-top North. The outward normal is rounded
to the nearest of N/NE/E/SE/S/SW/W/NW; a diagonal element can therefore show NE/SW
or NW/SE. Map labels combine section number and heading, such as 2.E or 3.NW.
A horizontal segment has North/South sides; a vertical segment has East/West.
Panning and zooming do not rotate these map-relative labels. Numeric 0/1 indices
remain an internal storage detail; no data migration or route remapping is needed.
Runtime passage behavior, permissions, viewer secrecy and migration 10 are
unchanged. See ../Passages.md and ../Patch/portal-compass-exits.md for details.
Looking Glass UVTT v2 stores only complete authored graphs, never temporary
Unconfigured draft state or runtime discovery/lock overrides.

## Moving the portal editor and reading the overview

Drag the Portal configuration title bar to expose underlying map artwork. Keyboard
users can focus the title bar and move it with arrow keys (10 px; Shift+arrow 50 px).
Center re-centers it. Positions are remembered only while this page remains open;
resize clamps the popup back into the viewport. The modal remains native/modal,
with a lighter backdrop: moving it does not enable accidental map edits underneath.

Portal overview on the toolbar shows the current authored wall draft. Overview of
pending portals inside the popup includes its un-applied local changes. The grid
contains section, compass side, role, initial state, secret discovery outcome,
paired Exit and incoming Entries. All sides are listed, including None and
Unconfigured. Shared Exits list every incoming Entry. It is read-only and does not
send HTTP requests, validate/apply, reveal or save. State labels are authored initial
states, not runtime lock/discovery status. Close/Escape returns to the previous
dialog without discarding pending configuration. The overview can also be moved.

The overview is a snapshot when opened; close/reopen it after subsequent edits.
Its table scrolls horizontally on small screens, and dialog height is bounded by
the viewport. Existing Cancel/Apply, stale-draft checks and Undo/Redo remain intact.
See ../Patch/portal-tools.md for deployment, testing and rollback.

## Portal label backing

Compass/section labels now use dark rounded semi-transparent backing badges
(rgba(8,12,20,.78)) and white semibold monospace text. A 50%-opacity white border
helps separate a badge from surrounding artwork. Each badge is measured from its
actual text rather than a fixed width, so larger section numbers also fit.

At any zoom, text remains 12 screen pixels, with 4 screen pixels of horizontal
padding and 2.5 vertically. Border width is one non-scaling screen pixel. Labels
are rendered together above all wall lines, and never intercept mouse/touch input.
They are an editor overlay only and are not stored in wall data, exported into
UVTT or added to player images. See ../Patch/portal-visibility.md.

## Apply without closing the portal configuration popup

Use Apply configuration to draft as often as needed while configuring sections.
After each successful Apply, the current section, dragged popup position and scroll
position remain; the side panels reload from the just-applied draft so pair IDs,
routes and the overview remain synchronized. Continue editing immediately without
reopening. Each changed Apply can later be undone independently in the main editor.

Use the separate Close button to leave the popup. Close, Cancel pending edits and
Escape do not implicitly apply newer changes, nor do they revert earlier Applies.
The main editor's Save wall set is still required to persist the draft. A live
status message inside the popup distinguishes applied changes from newer pending
edits and incomplete configurations. Stale/invalid submissions leave the popup
open with an error and do not silently update the baseline.

The endpoint-coordinate Edit dialog and its own Apply/Cancel behavior are unchanged.
This follow-up does not install or remove the preceding label/highlight visibility
patch; its style/script files and cache URLs are preserved when already installed.
See portal-configuration-apply.md and ../Patch/portal-apply-open.md.
